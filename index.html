Architecture case study

Zesto — closing a real race condition.

A solo-built food delivery platform used to practice architecture at production depth, not a tutorial walkthrough.

Problem

A race condition, not a hypothetical

The OTP rate-limit check was read-then-write: count recent requests, then insert. Two near-simultaneous requests for the same phone number could both read a count under the limit and both pass — the cap could be bypassed entirely.

Decision

Redis over a SQL lock

Migrated OTP storage from SQL Server to Redis and rebuilt the rate-limit and cooldown checks around Redis's atomic primitives — closing the race structurally instead of patching around it with a database lock.

Built

Atomic by construction

Cooldown via an atomic claim, rate limiting via an atomic increment wrapped in a transaction with the TTL set in the same step. Verified with integration tests run against a real Redis container, not mocks.

Trade-off

Fixed window, deliberately

This produces a looser fixed-window limit than the original sliding-window SQL query — a boundary burst can clear slightly more than the nominal cap. Accepted on purpose: the looseness is bounded and harmless for OTP rate limiting.
